# Frontend Standards (apps/web)

How the Shipment Tracker web app is built. Every rule below describes what `apps/web` does now.
When you write new code, follow the code around it.

## Stack

- **Next.js 15** (App Router) with **React 19** and TypeScript `strict`. Imports use the alias
  `@/` (`@/components/...`, `@/lib/api`).
- **Ant Design 5** for components, with `@ant-design/icons` (a few icons come from
  `@phosphor-icons/react` and `src/components/icons`).
- **Tailwind CSS v4** for all styling. The shared look lives in `src/styles/ui.ts`.
- **@tanstack/react-query 5** for all server data, and **dayjs** for dates.
- **Vitest** for tests.

## A client-side app

- Every page runs in the browser. A `page.tsx` is either a `"use client"` component, or a thin
  server wrapper that only renders a client view. The wrapper may also export `metadata` (the tab
  title), wrap the view in `<Suspense>` when it reads the URL with `useSearchParams`, or
  `redirect()`.
- **No server-side data fetching.** There are no server components that fetch, no route handlers
  (`route.ts`), no server actions and no middleware. All data comes from the Encore API, called in
  the browser.
- `next.config.ts` sets the security headers: the Content-Security-Policy, which allows only the
  app, `blob:` and the API origin, and `no-referrer` on the token pages (`/track`, `/haulier`,
  `/import-instructions`, `/register`).

## Folder layout

```
src/
├── app/<feature>/
│   ├── page.tsx              # thin route entry
│   ├── _components/          # components only this feature uses
│   ├── _lib/                 # pure helpers and constants of the feature (+ their *.test.ts)
│   └── [id]/ …               # sub-routes (detail pages, tabs)
├── components/               # shared UI: PageHeader, SectionCard, DataTable, AppModal, …
├── hooks/                    # data hooks: use<Thing>.ts, shared query keys (customerKeys.ts, …)
├── lib/                      # pure helpers (date, money, phone, …), api/, auth/, theme/, toast.ts
└── styles/                   # ui.ts (class constants), globals.css
```

- Put code in its feature (`app/<feature>/_components`, `_lib`) by default. Move it to
  `components/`, `hooks/` or `lib/` only when a second feature needs it.
- Keep route files thin. Split a large component into focused files of the feature.

## Talking to the API

- Use the client from `@/lib/api`:
  - `api`, for signed-in pages. Its fetcher adds `Authorization: Bearer <token>` and, for a
    superadmin, `X-Acting-Company`. On a 401 it ends the session once and opens `/login`.
  - `publicApi`, for the token pages (tracking, haulier link, registration). It never sends the
    session.
  - `keepaliveApi` / `clientForBody(body)`, for saves that must arrive when the tab closes.
  - `apiFileUrl(contentUrl)`, for a file link. The API returns `contentUrl` with a short-lived
    signed token, so a plain `<a href>` or `<img src>` works without the auth header.
- Take types from the client: `import type { controllers, interfaces } from "@/lib/api/client"`
  (for example `interfaces.NoteItem` and `controllers.NoteCreateRequest`).
- **`src/lib/api/client.ts` was generated by Encore once and is now edited by hand.** When an
  endpoint is added or changed, edit its method and types in the matching service namespace by
  hand, to match the controller. Do not regenerate it (`pnpm gen` / `gen:client`), because that
  replaces the whole file and loses the hand edits.
- **Related data comes from the backend.** If a screen needs something about a related record (a
  shipment's quote sales person, a customer's name, warehouse plates), the API response it already
  loads must carry it. Do not add a second request from the browser. Add the field on the server
  instead (see `rules/encore-ts-standards.md`, "Calling other services").

### Data hooks

Queries and mutations live in hooks in `src/hooks/`, about 90 files of them. Some feature
components still call `useQuery` themselves; a new data read or write gets a hook:

```typescript
// src/hooks/useCustomerNotes.ts (shortened)
export const useCustomerNotes = (customerId: string) => {
  const queryClient = useQueryClient();
  const key = ["customer-notes", customerId];

  const query = useQuery({
    queryKey: key,
    queryFn: () => api.customers.noteList(customerId),
    enabled: !!customerId,
  });

  const invalidate = () => {
    void queryClient.invalidateQueries({ queryKey: ["customers"], refetchType: "none" });
    return queryClient.invalidateQueries({ queryKey: key });
  };

  const createMutation = useMutation({
    mutationFn: (params: controllers.NoteCreateRequest) => api.customers.noteCreate(customerId, params),
    onSuccess: invalidate,
  });

  return { notes: query.data?.data ?? [], isLoading: query.isLoading, isError: query.isLoadingError, createNote: createMutation.mutateAsync };
};
```

- After a write, invalidate every query that shows what changed, including other screens' lists.
  Mark a list stale with `refetchType: "none"` when it is not on screen. When several hooks share
  keys, keep the keys in one file (`customerKeys.ts`, `salesQueryKeys.ts`, `truckingKeys.ts`,
  `warehouseKeys.ts`).
- The defaults (`Providers.tsx`): `staleTime` 1 minute, no refetch on window focus, one retry.

### Errors and messages

- Show the server's own sentence: `apiErrorMessage(err)` returns the API's message, or "the server
  could not be reached". Do not invent a reason on the client. `isNotFound(err)` tells a missing
  record apart from any other failure.
- Show messages with `useToast()` from `@/lib/toast`. It is built on antd's `App` context, and
  errors and warnings stay on screen until clicked.

### Permissions

- The API decides. The UI only hides or disables what the user may not do, using `useAuth()` and
  the role hooks in `@/lib/auth/AuthContext` (`useCanManageCustomers`, `useCanManageDocuments`,
  …), the flags the API returns with a record, or `SuperadminOnly` for whole pages.

## Styling: one look

- **Tailwind classes only.** Use inline `style` only for a value computed at runtime (for example
  the conditional-format colours that `makeStyleFor` gives a field). No `<style>` tags, CSS
  modules or hard-coded colours in `style`.
- **Take the look from `src/styles/ui.ts`** and the shared components, never a local one-off title,
  card, table or button style:
  - Constants: `PAGE_TITLE`, `PAGE_SUBTITLE`, `MODAL_TITLE`, `CARD`, `CARD_BAR`, `CARD_TITLE`,
    `LABEL_TEXT`, `HINT`, `EMPTY`, `REF`, `KPI_VALUE`, `TH`, `TD`, `TD_TOTAL`, `LINK`, `HEADING`,
    `EMPTY_STATE`, `BTN`, `BTN_PRIMARY`, `BTN_DANGER`, `BTN_GHOST`, `BTN_SM`, `BTN_BAR`,
    `BTN_BAR_PRIMARY`, `ADD_BTN`, `ICON_BTN`, `ICON_BTN_GHOST`, `ICON_BTN_DANGER`, `CHIP`,
    `CHIP_ON`, `INPUT`, `TEXTAREA`.
  - Components (`src/components`): `PageHeader`, `SectionCard` (and `PillTabs` in the same file),
    `DataTable`, `AppModal`, `ConfirmModal`, `Pill`, `Badge`, `StatusBadge`, `RecordTabs`,
    `KpiTile`, `EmptyCell`, `InfoRow`.
- Type and colour, as `ui.ts` sets them out: Inter only (`font-mono` is Inter too), sizes 10, 11,
  12, 13, 14, 16, 20 and 22 px only. Colours are slate for text and lines, indigo for the accent,
  and emerald / amber / red / sky for status. Use `tabular-nums` for figures in columns and `REF`
  for codes people read out.
- To add to a constant, append the class: `` `${TH} w-[120px]` ``. To change something the
  constant already sets, add `!`: `` `${TH} !text-center` ``. Tailwind sorts classes itself, so
  the order in `className` does not decide.
- antd's styles sit in a CSS layer under Tailwind's utilities (`StyleProvider layer` in
  `lib/theme/ThemeProvider.tsx`, `@layer` in `globals.css`), so a Tailwind class on an antd
  component wins. antd's theme tokens are in `lib/theme/themeConfig.ts`.

## Components and code style

- Write function components with hooks. The only class is the error boundary in
  `FilePreviewDialog.tsx`, because React allows error boundaries only as classes.
- Give props an `interface`. Avoid `any`: the web's lint allows it, but the code uses it only a
  handful of times.
- Name event handlers `handle…` (`handleSave`, `handleKeyDown`).
- Use early returns, descriptive names, and comments that say *why*.
- Accessibility: use real `<button>`s or antd `Button`s for actions, and give icon-only buttons an
  `aria-label`. An element that is clickable but not a button needs `role`, `tabIndex={0}` and a
  keyboard handler.
- Use the helpers instead of formatting by hand: dates through `lib/date.ts` (values are stored
  as ISO and shown in the Czech format), money through `lib/money.ts`, phones through
  `lib/phone.ts`.

## Tests and checks

- Unit tests are Vitest files `src/**/*.test.ts`, next to the module they test. They cover pure
  logic: helpers, column and filter definitions, hook logic split into plain functions.
- `pnpm --filter web test`, `pnpm --filter web typecheck` and `pnpm --filter web lint`. Errors
  under `.next/types/` are stale build output, so ignore them or delete `.next/types`.
- The dev server runs on port 3001 (`pnpm --filter web dev`). The API is at `NEXT_PUBLIC_API_URL`,
  `http://localhost:4001` by default.

## Working principles

- Implement the whole feature as asked: every tab, dialog and state. Leave no TODOs or
  placeholders.
- Read the existing feature first and follow its patterns. Do not change the look or the behaviour
  of what is there unless asked.
- If you are not sure what is wanted, say so instead of guessing.
